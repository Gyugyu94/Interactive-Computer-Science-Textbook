# 개발자를 위한 운영체제 시각 강의 기획안

내 코드가 컴퓨터에서 어떻게 실행되는지, **한 화면에 한 가지씩** 이해하는 웹 강의다. 읽는 흐름은 프레젠테이션처럼 앞뒤로 넘긴다. 코드나 그림에서 변화가 일어나는 순간에는 같은 도식 안에서 무엇이 어디로 이동하고 어떤 값이 바뀌는지 보여준다.

첫 강의는 사용자가 제공한 **Day 1 — CPU와 RAM부터 이해하기**로 만든다. JavaScript, React Native, Node.js 예시는 운영체제 개념을 웹·앱 개발자가 익숙한 코드와 연결하는 데 사용한다.

## 한 화면에서 학습하는 방식

- **제목은 질문 하나.** ‘CPU는 명령을 어떻게 실행할까?’처럼 화면에서 답할 질문을 보여준다. 설명은 핵심 한 문장과 필요한 코드나 그림으로 구성한다.
- **앞뒤 화면에서 같은 그림을 이어 쓴다.** SSD, RAM, CPU의 위치와 이름을 유지한다. SSD에서 RAM으로 넘어오는 부분을 본 다음, 같은 RAM에서 CPU가 명령을 가져가는 흐름을 본다.
- **순서가 중요한 곳에서 움직임을 쓴다.** 한 번에 다음 변화만 강조한다. 시간이 필요한 그림은 학습자가 `한 단계` 또는 `다시 보기`로 살펴보고, 화면은 `이전`과 `다음`으로 직접 넘긴다. 키보드나 터치로도 같은 조작을 할 수 있다.
- **정의와 요약은 정지 화면으로 읽는다.** 각 애니메이션은 끝난 상태와 짧은 설명을 남긴다. 움직임 줄이기 설정을 켜면 같은 순서를 상태 그림과 글로 보여준다.

## Day 1 화면 구성

원문의 순서를 따른다. CPU 구성 요소와 실무 예시는 각각 한 화면에 집중할 수 있도록 나눈다.

| 화면 | 화면에서 다룰 내용 | 시각 자료 |
| --- | --- | --- |
| **1. 프로그램은 어디에서 실행될까?** | RAM은 실행에 필요한 코드와 데이터의 작업 공간이고, CPU는 명령을 실행한다. | ‘내 코드 → 실행 가능한 명령 → RAM → CPU’를 순서대로 밝힌다. |
| **2. CPU는 명령을 어떻게 실행할까?** | Fetch → Decode → Execute를 `10 + 20`의 단순화한 명령으로 따라간다. | RAM에서 가져온 `ADD` 명령이 강조되고, 실행 단계에서 레지스터의 결과가 `30`으로 바뀐다. |
| **3. SSD에 파일이 있는데 왜 RAM이 필요할까?** | SSD는 파일을 저장하고, 프로그램을 실행할 때 필요한 코드와 데이터는 RAM에 들어온다. | 같은 SSD·RAM·CPU 그림에서 필요한 부분을 RAM으로 가져오는 모습을 보여준다. RAM 쪽에는 코드, 데이터, 스택, 힙을 표시한다. |
| **4. CPU에서 실제로 무엇이 실행될까?** | 앱의 프로세스 안에는 스레드가 있고, OS는 실행할 스레드에 CPU 시간을 배정한다. | 프로세스 상자를 펼쳐 스레드를 보여주고, 실행 대상으로 선택된 스레드 하나를 CPU 코어에 이어 준다. |
| **5. 앱을 누르면 첫 화면까지 무엇이 일어날까?** | 실행 중인 인스턴스가 없는 React Native 앱이 시작되는 흐름을 본다. | 축구 앱 아이콘에서 시작해 OS, 프로세스, 런타임과 스레드를 차례로 보여준 뒤 첫 앱 화면이 나온다. |
| **6. 코어는 무엇일까?** | 코어는 명령어를 실행하는 단위다. OS가 실행 가능한 스레드를 코어에 배치한다. | 여러 코어를 펼쳐 서로 다른 스레드가 배정되는 모습을 보여준다. |
| **7. 레지스터는 어디에 쓰일까?** | 레지스터는 CPU 안의 작은 저장 공간이다. 연산에 쓰는 값과 결과를 담을 수 있다. | 2번 화면의 `10`, `20`, `30`을 다시 써서 연산 전후의 레지스터 값을 비교한다. |
| **8. 캐시는 왜 필요할까?** | CPU는 필요한 명령이나 데이터가 가까운 캐시에 있으면 RAM까지 접근하는 시간을 줄일 수 있다. | 같은 데이터를 캐시에서 찾은 경우와 RAM에서 가져온 경우의 경로를 번갈아 강조한다. |
| **9. React Native 앱의 애니메이션은 왜 끊길까?** | JS 스레드의 작업이 밀리면 그 스레드에 의존하는 애니메이션 갱신이 늦을 수 있다. | 프레임 마감선과 작업 막대를 겹쳐, 어느 갱신이 늦어졌는지 보여준다. [React Native 성능 문서](https://reactnative.dev/docs/performance) |
| **10. Node.js는 왜 응답을 늦게 보낼까?** | 오래 실행되는 동기 계산이 이벤트 루프의 다음 작업을 늦출 수 있다. | 같은 스레드의 타임라인에 계산 구간과 뒤에서 기다리는 콜백을 배치한다. [Node.js 이벤트 루프 문서](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop) |
| **11. 오늘 기억할 네 가지** | CPU는 명령을 실행한다. RAM은 실행 중 필요한 코드와 데이터를 담는다. 저장된 내용은 실행에 필요한 만큼 메모리로 들어온다. CPU가 실행하는 단위는 기계 명령이다. | 첫 화면의 도식을 다시 보여준다. |
| **12. 확인 문제** | 원문의 질문 다섯 개에 답을 먼저 떠올린다. | `정답 보기`를 누르면 해당 질문의 답과 근거 그림을 펼친다. |

JavaScript 덧셈 예시의 레지스터와 명령은 원리를 설명하기 위한 모델로 표시한다. 실제 JavaScript 엔진이 같은 코드를 어떻게 실행하는지는 **Day 2 — 명령과 기계어**에서 이어서 설명한다. 첫 강의에서 소개한 프로세스·스레드·스케줄링과 스택·힙은 후속 강의에서 같은 그림을 확장한다.

## 애니메이션 예시 — Fetch → Decode → Execute

1. 처음에는 화면에 RAM, CPU, 레지스터만 놓는다. 레지스터에는 이미 `10`과 `20`이 들어 있다.
2. **Fetch.** `한 단계`를 누르면 현재 명령 `ADD`가 RAM 쪽에서 CPU 쪽으로 이동한다.
3. **Decode.** 같은 명령에서 ‘더하기’에 해당하는 부분이 강조된다. 옆에 ‘두 값을 더하는 명령을 확인합니다’가 나타난다.
4. **Execute.** 레지스터 값 두 개가 강조되고 결과 위치가 `30`으로 바뀐다. 다음 명령을 가리키는 표시가 한 칸 이동한다.

## 참고 사례와 검증

- **Bartosz Ciechanowski의 Mechanical Watch**는 부품 설명 바로 옆에 조작 가능한 그림을 두고, 그 부품이 다음 단계와 어떻게 이어지는지 보여준다. 글과 그림을 읽는 순서를 참고한다. [Mechanical Watch](https://ciechanow.ski/mechanical-watch/)
- **Red Blob Games의 A* 설명**은 한 단락에서 설명한 과정을 같은 그림에서 한 단계씩 앞으로·뒤로 보게 한다. 명령 실행처럼 상태가 연속해서 바뀌는 화면에 이 방식을 적용한다. [A* 시각 강의](https://www.redblobgames.com/pathfinding/a-star/introduction.html)
- **Nand2Tetris의 CPU 에뮬레이터**는 실행 중 명령, RAM, 레지스터를 한 화면에서 볼 수 있게 한다. Day 1은 이 구성을 작은 덧셈 예시로 보여준다. [CPU 에뮬레이터 안내](https://nand2tetris.github.io/web-ide/about/)

운영체제 수업 연구에서는 개념을 배운 뒤에도 구체적인 상황에 적용하기 어려운 경우가 보고됐다. 첫 화면을 검토할 때 웹·앱 개발자에게 그림을 본 뒤 ‘왜 RAM이 필요한가’와 ‘어느 단계에서 결과가 바뀌었는가’를 자기 말로 설명하게 한다. [운영체제 개념 이해 연구](https://www.cs.oberlin.edu/~ctaylor/pubs/OSCI14.pdf)

## 첫 제작 범위

Day 1의 **큰 그림, CPU의 명령 실행, SSD와 RAM** 세 화면을 먼저 만든다. 화면 넘기기와 단계별 재생을 실제 브라우저에서 확인하고, 같은 읽기 방식으로 나머지 Day 1을 이어 붙인다. 공통 화면은 제목, 본문, 시각 자료, 이전·다음 버튼으로 구성한다. 각 화면은 본문과 시각 자료의 단계만 정의한다.
